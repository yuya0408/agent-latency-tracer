# 切り分けの手順書

事例ごとに「症状 → 最初の仮説 → 決め手になったspan・属性 → 修正 → 修正の確かめ」の順で書く。
「修正の確かめ」は、直した後に同じ条件で症状が消えたのをトレースで見たか(済み・未・対象なし)。
根拠のトレースは[traces/](../traces/)に置く。番号は[README](../README.md)の事例集の番号。

## 1 独立したツール呼び出しを、1つずつ待つ(逐次await)

- 再現: 注入(`PITFALLS=1`、2026-11-05、GPUの1回目)。計装と手順書を確かめるために入れた

- 症状: 1問が約44秒(基準は約42.5秒)。差はツールの数と待ち時間で決まり、この質問では2秒弱
- 決め手: エージェント側の`execute_tool`(と`MCP send`)の開始が階段状になる。前の呼び出しが終わった時刻に、次が始まる。
  2回目の返事では、`find_records`が28.50秒から0.92秒、`aggregate_records`が29.42秒から。基準では2つとも同じ時刻に始まる

- 修正の確かめ: 済み(基準の回。同じ質問で、`execute_tool`が同じ時刻に始まり、1問が約44秒から約42.5秒)
- 似た症状との見分け: #2とは、どちら側が階段になるかで分かれる(下)。イベントループの遅延を測る計装は要らなかった

## 10 プロンプトの先頭が毎回変わり、プレフィックスキャッシュが効かない

- 再現: 注入(`PITFALLS=10`、2026-11-07、GPUの2回目)。エージェントがLLMを呼ぶたびに、秒までの現在時刻を書いたシステムプロンプトを
  先頭に付ける。プロンプトの雛形を呼び出しごとに埋める書き方にあたる
- 条件: 1つのセッションで、温め用の質問の後に仮の質問6問を順に。基準も同じ形で、同じGPUの回の中で流した
- 症状: LLMの1回の呼び出しの、vLLM側のTTFT(`vllm.time_to_first_token_ms`)の中央値が88ms → 894ms(374〜1,353ms)。
  会話が積み上がるほど伸び、最後の質問(入力4,482トークン)で1,353ms
- 決め手: chat spanの`vllm.cached_tokens`。基準は温めた後の呼び出しで入力の93%(例: 入力1,551のうち1,472)、先頭の時刻ありではどの呼び出しでも16。
  vLLMの`/metrics`の`prefix_cache_hits_total`の増分でも、基準は31,061トークン中27,584、先頭の時刻ありは47,692トークン中240
- 原因: Qwen3のチャットテンプレートはシステムプロンプトをツール定義より前に書くので、時刻のところで一致が切れ、ツール定義も会話も毎回読み直す。
  16はvLLMのブロック(16トークン)1つ分で、時刻より前の部分だけが一致している
- 修正: 変わる値をプロンプトの先頭に置かない(時刻を入れない・日付だけにする・最後のユーザーメッセージの側に置く)。基準の書き方
- 修正の確かめ: 済み(同じGPUの回の基準。`cached_tokens`が入力の約9割、TTFTの中央値88ms)
- 似た症状との見分け: #8 長い入力もTTFTが伸びるが、`cached_tokens`は大きいまま。先頭の時刻は入力が短くても`cached_tokens`が16前後。
  会話を40メッセージで切った直後も1回だけ外れるが、そのときは`input_tokens`が前の呼び出しより減る(今回は起きなかった)
- 見落としやすい点: 6問の合計時間では比べられない。6問中5問でLLMの呼び出しの回数が変わった(全体で12回 → 15回)。本当の日付が入ったことが
  効いたのかは確かめていない。呼び出しごとの値で読む
- 根拠のトレース: [先頭の時刻あり、「A社の未出荷の受注と、品目X001の在庫は?」](../traces/10/gpu2-q2.html)、[基準](../traces/base/gpu2-q2.html)

## 12 同時に来た質問が、推論サーバの待ち行列で待たされる

- 再現: 条件の注入(2026-11-05、GPUの1回目)。同時の数は、基準の回の1問の時間(中央値約23.5秒)から、
  300人の繁忙時の99%点として6問と決めた([設計書](DESIGN.md)の#12の並行数)
- 条件: vLLMのコンテナを作り直してKVを22,976トークンにそろえ、仮の質問6問のセッションを温めてから一斉に投げた
- 結果: 待ち行列は起きなかった。vLLMの`request_queue_time_seconds`は22回のリクエストで合計0.33ms、preemptionは0回。
  1問ずつのときより少し長くなっただけ(「A社の未出荷の受注と、品目X001の在庫は?」42.5秒 → 45.1秒、「出張旅費の精算のルールは?」16.2秒 → 19.2秒)。
  6問の入力を合わせても約1.5万トークンで、KVに収まった
- 決め手(待ちが出たときに見るもの): まず`/metrics`の`num_preemptions_total`、次に`llm_request` span・chat spanの`vllm.queue_time_ms`と`num_requests_waiting`。
  vLLMは今の空きでリクエストを受け入れ、生成が進んでKVが足りなくなってから、走っている処理を一度外して後で計算し直す(preemption)。
  なので、KVの不足は待ち行列より先にpreemptionとして出る(`toolcall-serving-bench`の`docs/engines.md`、vLLM 0.31.0)
- 比べ方の注意: 道筋が変わった質問は比べられない(6問のうち2問で、LLMの呼び出しの回数が変わった)。質問の合計時間ではなく、
  LLMの1回ごとの値(1トークンの時間`vllm.mean_itl_ms`など)で比べる
- 同時に乗った数(`llm_request` spanの重なりから数えた): 約45秒のうち、6本が2.9秒、5本が10.8秒、4本が4.8秒、3本が4.7秒、
  2本が2.4秒、1本が18.6秒。1トークンの時間は、1問ずつの約60.5msから61〜67msに伸びた(1割以内)
- 書けること: 同時6問、入力の合計がKVの約3分の2では、待ちもpreemptionも出なかった。
  KVに入るかの目安は「同時の数 × 1リクエストの最大の長さ(入力＋出力) ≤ KVのトークン数」(`toolcall-serving-bench`のADR-0005と同じ式)。
  このrunの1リクエストは入力が最大約3,600トークン、出力が最大約280トークンなので、22,976トークンなら約5.9リクエストまで入る計算になる。
  6本が同時に乗ったのは約3秒だけで、ほとんどの時間はツールを待つ質問がLLMから降りていた。6本のときも
  preemptionは0回だったので、KVに収まっていた(各時点のKVの使用量そのものは見ていない)
- 修正の確かめ: 対象なし(待ちが起きなかった)
- 根拠のトレース: [6問同時のうち「A社の未出荷の受注と、品目X001の在庫は?」](../traces/12/gpu1-q2-concurrent.html)

## M1 ツール定義が膨らむ(データの種類ごとのツール)

- 再現: 注入(`PITFALLS=M1`、2026-11-07、GPUの2回目)。MCPサーバが、データの種類ごとに検索・1件取得・集計のツールを作る
  (15種類で45個、文書検索と合わせて46個)。APIを1つずつ包む形
- 条件: 先頭の時刻の項目と同じ。先頭の時刻と重ねた回(`PITFALLS=10,M1`)も流した
- 症状: プレフィックスキャッシュが空の呼び出し(温め用の質問)だけが遅い。入力1,305 → 9,548トークン、vLLM側のTTFT 373ms → 3,021ms。
  温めた後は、入力が最大10,624トークンでもTTFTの中央値95ms(基準88ms)。先頭の時刻と重ねると、毎回約1万トークンを読み直し、
  TTFTの中央値3,324ms(3,036〜3,671ms)
- 決め手: chat spanの`llm.request.tool_count`(5 → 46)と`gen_ai.usage.input_tokens`。そのうえで`vllm.cached_tokens`が入力の99%なら、
  遅れはキャッシュが空の1回だけ。`cached_tokens`が小さければ先頭の時刻のような先頭の変化と重なっている
- 修正: 操作ごとの汎用ツールにする(基準)。種類ごとのツールのままにするなら、定義をプロンプトの先頭に固定し、先頭を変えるもの(先頭の時刻)と重ねない
- 修正の確かめ: 済み(同じGPUの回の基準。`tool_count`が5、温め用の質問の入力1,305トークン)
- 書けること: キャッシュが効いている限り、ツール定義の長さは2回目の呼び出しからはほとんど遅れにならない。遅れが出るのは、キャッシュが空のとき
  (新しいプロセスの最初、キャッシュから追い出されたとき)と、先頭が毎回変わるとき。キャッシュが空のときの約1万トークンの読み込みは約3秒
  (L4・Qwen3-8B・vLLM 0.31.0)
- 答えについては言えない: この回の種類ごとのツールは、条件を「等しい」でしか書けなかった(範囲が書けない)。ツールの数と一緒に条件の書ける幅も
  変わっていたので、基準で答えられた3問(未出荷の受注と在庫・9月の集計・10月中の請求)がどれも「0件」になったのが、ツールが増えたせいか
  条件が書けないせいかは分けられない。ツールの作りの不備で、元のAPIに期間の指定があれば、包んだツールにも「から」「まで」の引数が出るのが普通。
  引数は記録していないので、トレースでも確かめていない。遅れの値(`cached_tokens`・TTFT・入力の長さ)はLLMの呼び出しごとに読んでいるので、この不備の影響を受けない。
  ツールを直し、次にGPUを使う段階で種類ごとのツールの回を1回足す
- 根拠のトレース: [種類ごとのツールあり、温め用の質問](../traces/M1/gpu2-warmup.html)、[種類ごとのツールあり、「A社の未出荷の受注と、品目X001の在庫は?」](../traces/M1/gpu2-q2.html)、

## 自然に発生: 計装の保存がイベントループを止める

[設計書](DESIGN.md)の§7の2・3・11から。

- 再現: 自然に発生(2026-10-04、段階2a。2026-10-27に、送り先をCloudWatchにしたときにも同じ形で起きた)
- 症状: HTTP越しのツール呼び出しで、エージェントの`MCP send tools/call`がサーバの`tools/call`より12〜100ms長い(80ms前後が多い)。
  CloudWatchへ送った試しのスクリプトでは、子spanを1本作って閉じただけの親spanが537msになった
- 最初の仮説: 記録に無い(最初に、通信かサーバの中かを分けた)
- 決め手(順に):
  - HTTPの層のspan(`POST /mcp`)を足すと、差は通信ではなくサーバの中、それも「ツール処理が終わってから応答を送り始めるまで」にあった
  - asyncioのデバッグモード(`loop.slow_callback_duration`を20ms)で、その区間にイベントループが30〜70ms止まっていた。サーバの計装をオフにすると消えた
  - 保存1回ごとに時間を測ると、`tools/call` spanの保存だけがときどき約67msかかっていた。SQLiteは、前の書き込みから100ms以上空くと
    commitに65〜75msかかる(連続なら4ms)
- 原因: `SimpleSpanProcessor`は、spanが終わるたびに呼び出し元のスレッドで同期的に保存する。その間はイベントループが止まる
  (#2と同じ形。`span.end()`も`export()`も同期の関数で、`await`を入れる余地が無い)。CloudWatchへの送信では、署名とHTTPSの往復を待つので1桁大きくなる
- 修正: `BatchSpanProcessor`(キューに入れ、別のスレッドがまとめて保存する)に変えた。差は3〜11msになった。
  今はどのプロセスも`build_tracer_provider(..., batch=True)`([tracing/instrumentation.py](../tracing/instrumentation.py))
- 修正の確かめ: 済み(上の差が3〜11msになった)
- 代わりに起きること: 保存は最大500ms(`BATCH_EXPORT_INTERVAL_MS`)遅れる。終了時に`shutdown()`しないと、キューに残ったspanが失われる
- 似た症状との見分け: #2(ツールの中のブロッキング呼び出し)とは、計装をオフにすると消えるかで分かれる。
  消えるなら計装、消えないならツールのコード。spanを作ること自体は1個あたり約0.03msで、問題は保存のほう
- 見落としやすい点: 測るための仕組みが、測っている対象を遅くする。手元のSQLiteやこのPCのディスクに固有の部分はあるが、
  「同期的な保存やログの送信がリクエストの処理を止める」形は実務でも起きる

## 自然に発生: ツールを呼ぶ応答だけ、TTFTが約500ms長い

[設計書](DESIGN.md)の§7の10から。

- 再現: 自然に発生(2026-10-11に手元の2B(llama.cpp)で気づき、2026-11-01にvLLM(Qwen3-8B)で原因を確かめた)
- 症状: chat spanのTTFT(`llm.time_to_first_token_ms`)が、ツールを呼ぶ応答では約600ms、答えを返す応答では50〜100ms。
