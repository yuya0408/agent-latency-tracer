# 切り分けの手順書

事例ごとに「症状 → 最初の仮説 → 決め手になったspan・属性 → 修正」の順で書く。
根拠のトレースは[traces/](../traces/)に置く。番号は[README](../README.md)の事例集の番号。

## 1 独立したツール呼び出しを、1つずつ待つ(逐次await)

- 再現: 注入(`PITFALLS=1`、2026-11-05、GPUの1回目)。計装と手順書を確かめるために入れた
- 条件: 「A社の未出荷の受注と、品目X001の在庫は?」を、温めたセッションで3回。LLMは1つの返事でツールを2〜3個呼ぶ
- 症状: 1問が約44秒(基準は約42.5秒)。差はツールの数と待ち時間で決まり、この質問では2秒弱
- 決め手: エージェント側の`execute_tool`(と`MCP send`)の開始が階段状になる。前の呼び出しが終わった時刻に、次が始まる。
  2回目の返事では、`find_records`が28.50秒から0.92秒、`aggregate_records`が29.42秒から。基準では2つとも同じ時刻に始まる
- 修正: `asyncio.gather`で同時に呼ぶ(基準の書き方、[system/agent.py](../system/agent.py))
- 似た症状との見分け: #2とは、どちら側が階段になるかで分かれる(下)。イベントループの遅延を測る計装は要らなかった

## 2 asyncの中のブロッキング呼び出し(同時に呼んでも順になる)

- 再現: 注入(`PITFALLS=2`、MCPサーバのモックが`time.sleep`で待つ。2026-11-05、GPUの1回目)
- 条件: #1と同じ質問を3回
- 症状: 1問が約44秒。#1とほぼ同じで、合計時間だけでは区別できない
- 決め手: エージェント側の`execute_tool`は同じ時刻(9.55秒)に3つそろって始まるが、サーバ側の`tools/call`の開始が
  9.61 → 9.83 → 10.07秒と階段状になる。`POST /mcp`は9.83秒に受け付けているのに、中の`find_records`は10.07秒まで始まらない。
  サーバのイベントループが`time.sleep`の間止まり、受け付けた次のリクエストに進めない
- 修正: 非同期の待ち(`asyncio.sleep`、非同期のクライアント)か、スレッドへ逃がす(`asyncio.to_thread`)
- 似た症状との見分け: #1はエージェント側が階段、#2はエージェント側がそろってサーバ側が階段。
  MCPサーバ側の計装が無いと、#2は「ツールの応答が遅い」としか見えない(エージェント側では、各`MCP send`がサーバでの処理より長くなる。
  `aggregate_records`は処理0.24秒に対して`MCP send`が0.54秒で、前の処理の終わりを待った分が乗る)

## 12 同時に来た質問が、推論サーバの待ち行列で待たされる

- 再現: 条件の注入(2026-11-05、GPUの1回目)。同時の数は、基準の回の1問の時間(中央値約23.5秒)から、
  300人の繁忙時の99%点として6問と決めた([設計書](DESIGN.md)の#12の並行数)
- 条件: vLLMのコンテナを作り直してKVを22,976トークンにそろえ、仮の質問6問のセッションを温めてから一斉に投げた
- 結果: 待ち行列は起きなかった。vLLMの`request_queue_time_seconds`は22回のリクエストで合計0.33ms、preemptionは0回。
  1問ずつのときより少し長くなっただけ(「A社の未出荷の受注と、品目X001の在庫は?」42.5秒 → 45.1秒、「出張旅費の精算のルールは?」16.2秒 → 19.2秒)。
  6問の入力を合わせても約1.5万トークンで、KVに収まった
- 決め手(待ちが出たときに見るもの): まず`/metrics`の`num_preemptions_total`、次に`llm_request` span・chat spanの`vllm.queue_time_ms`と`num_requests_waiting`。
  vLLMは今の空きでリクエストを受け入れ、生成が進んでKVが足りなくなってから、走っている処理を一度外して後で計算し直す(preemption)。
  なので、KVの不足は待ち行列より先にpreemptionとして出る(`toolcall-serving-bench`の`docs/engines.md`、vLLM 0.31.0)
- 比べ方の注意: 道筋が変わった質問は比べられない(6問のうち2問で、LLMの呼び出しの回数が変わった)。質問の合計時間ではなく、
  LLMの1回ごとの値(1トークンの時間`vllm.mean_itl_ms`など)で比べる。vLLMに同時に乗った数と1トークンの時間の伸びは、トレースから数える(未)
- 書けること: 同時6問、入力の合計がKVの約3分の2では、待ちもpreemptionも出なかった。
  KVに入るかの目安は「同時の数 × 1リクエストの最大の長さ(入力＋出力) ≤ KVのトークン数」(`toolcall-serving-bench`のADR-0005と同じ式)。
  このrunの1リクエストは入力が最大約3,600トークン、出力が最大約280トークンなので、22,976トークンなら約5.9リクエストまで入る計算になる。
  6問を投げても、ツールを待っている質問はLLMに乗っていないので、同時に乗る数は6より少なく、それで足りた(見込み。乗った数はトレースから数える)

## M2 MCPサーバへの呼び出しが、毎回コールドスタートする

- 再現: 自然に発生(2026-10-28、段階5。[設計書](DESIGN.md)の§7の12)
- 症状: `try_mcp.py`の8回の呼び出しに31秒かかった。サーバの`POST /mcp`はどれも数ms
- 最初の仮説: 記録に無い
- 決め手: 基盤側の`AgentCore.Runtime.Invoke`を並べると、8回すべて`session.id`が違い、
  うち4回は`latency_ms`が5〜7秒だった。サーバ側のspanだけでは見えない
- 原因: 2026-07-28版のMCPにはセッションが無く、SDKのクライアントは`Mcp-Session-Id`を送り返さない。
  AgentCoreはこのIDでmicroVMを振り分けるので、呼び出しのたびに新しいmicroVMが起動した
- 修正: クライアントで`Mcp-Session-Id`を送り返す。8回とも同じセッションになり、31秒が5.6秒に、
  基盤側は24〜989msになった
- 似た症状との見分け: READMEのM2の「クライアントの作り直し」は、同じ症状で原因が別。
  `server/discover`・`tools/list`のspanが毎回出るかで分かれる見込み(未再現)

## 自然に発生: 計装の保存がイベントループを止める

[設計書](DESIGN.md)の§7の2・3・11から。

- 再現: 自然に発生(2026-10-04、段階2a。2026-10-27に、送り先をCloudWatchにしたときにも同じ形で起きた)
- 症状: HTTP越しのツール呼び出しで、エージェントの`MCP send tools/call`がサーバの`tools/call`より12〜100ms長い(80ms前後が多い)。
  CloudWatchへ送った試しのスクリプトでは、子spanを1本作って閉じただけの親spanが537msになった
- 最初の仮説: 記録に無い(最初に、通信かサーバの中かを分けた)
- 決め手(順に):
  - HTTPの層のspan(`POST /mcp`)を足すと、差は通信ではなくサーバの中、それも「ツール処理が終わってから応答を送り始めるまで」にあった
  - asyncioのデバッグモード(`loop.slow_callback_duration`を20ms)で、その区間にイベントループが30〜70ms止まっていた。サーバの計装をオフにすると消えた
  - 保存1回ごとに時間を測ると、`tools/call` spanの保存だけがときどき約67msかかっていた。SQLiteは、前の書き込みから100ms以上空くと
    commitに65〜75msかかる(連続なら4ms)
- 原因: `SimpleSpanProcessor`は、spanが終わるたびに呼び出し元のスレッドで同期的に保存する。その間はイベントループが止まる
  (#2と同じ形。`span.end()`も`export()`も同期の関数で、`await`を入れる余地が無い)。CloudWatchへの送信では、署名とHTTPSの往復を待つので1桁大きくなる
- 修正: `BatchSpanProcessor`(キューに入れ、別のスレッドがまとめて保存する)に変えた。差は3〜11msになった。
  今はどのプロセスも`build_tracer_provider(..., batch=True)`([tracing/instrumentation.py](../tracing/instrumentation.py))
- 代わりに起きること: 保存は最大500ms(`BATCH_EXPORT_INTERVAL_MS`)遅れる。終了時に`shutdown()`しないと、キューに残ったspanが失われる
- 似た症状との見分け: #2(ツールの中のブロッキング呼び出し)とは、計装をオフにすると消えるかで分かれる。
  消えるなら計装、消えないならツールのコード。spanを作ること自体は1個あたり約0.03msで、問題は保存のほう
- 見落としやすい点: 測るための仕組みが、測っている対象を遅くする。手元のSQLiteやこのPCのディスクに固有の部分はあるが、
  「同期的な保存やログの送信がリクエストの処理を止める」形は実務でも起きる

## 自然に発生: `MCP send`とサーバの`tools/call`の間に隙間がある

[設計書](DESIGN.md)の§7の1から。

- 再現: 自然に発生(2026-10-04、段階2a)
- 症状: エージェントのトレースで、`MCP send tools/call`の始まりとサーバの`tools/call`の始まりの間に隙間がある
- 最初の仮説: 記録に無い
- 決め手: 隙間の中身は、親の無い別のトレースに記録されていた。HTTPの層のspan(`POST /mcp`)を足し、HTTPヘッダにも`traceparent`を載せると、
  その子として同じトレースの中に見えるようになった
- 原因: 2026-07-28版のStreamable HTTPでは、`Mcp-Param-*`ヘッダの検証にツールの引数の形が要るため、サーバが`tools/call`のたびに内部で
  `tools/list`のハンドラを呼ぶ(SDKの`Server.get_tool_input_schema`のdocstring)。これはMCPの層が`traceparent`を読む前に走る
- 修正: 計装の側で、HTTPの層のspanと`traceparent`を足した。内部の`tools/list`そのものは残している(一覧がメモリ上にあり約1ms)。
  `Server(..., get_tool_input_schema=...)`を渡すと無くなる
- 似た症状との見分け: 通信の遅れとは、`POST /mcp`の中に入っているかで分かれる
- 見落としやすい点: MCPの層だけを計装すると、この時間は「誰のものでもない隙間」になる。一覧の組み立てが重いサーバ(DBから読む等)では、
  ツールを呼ぶたびに効く

## 自然に発生: 同じ質問が2重に処理される(クライアントの自動再送)

- 再現: 自然に発生(2026-11-05、GPUの1回目、基準の回の「品目X001の入荷待ちの発注は?」)
- 症状: 手元では1回投げて75.7秒で答えが返った。その間、GPUは別の処理にも使われていた
- 最初の仮説: 記録に無い(1問だけ時間が長いので、トレースを開いた)
- 決め手: 手元の`InvokeAgentRuntime` spanは1つなのに、基盤側の`AgentCore.Runtime.Invoke`が同じ`session.id`で2つ並んでいた。
  1つ目は0秒から115秒(反復の上限で終わり、誰も受け取らない)、2つ目は60.9秒から14.6秒で、手元はこの答えを受け取った
- 原因: 手元のbotocoreの既定(読み取りタイムアウト60秒、タイムアウトしたら再送)。再送はライブラリの中で起き、手元のspanには現れない。
  AgentCoreは同じセッションの2つ目のリクエストを別の処理として始め、1つ目を止めない
- 影響: 捨てられた方もGPUを使い続け、後に流した2問と重なった(その値は捨てて流し直した)
- 修正: 読み取りタイムアウトを900秒、試行を1回に([scripts/invoke_agent.py](../scripts/invoke_agent.py))。実際のチャットでは、
  タイムアウトをエージェントの最長の処理より長くし、再送するなら前の処理を止める仕組みとセットにする
- 見落としやすい点: 呼び出し側の記録だけでは「1回で75秒」にしか見えない。基盤側のspanが無ければ気づけなかった

## 自然に発生: 接続プールが、切れたDBの接続を渡す

- 再現: 自然に発生(2026-11-05、GPUの1回目、基準の回の「出張旅費の精算のルールは?」)
- 症状: エージェントが500を返した。ほかの質問(文書検索を使わない)は通った
- 決め手: MCPサーバのログに`psycopg.OperationalError: consuming input failed: SSL error: unexpected eof while reading`と
  `discarding closed connection`。エージェントのログには`MCPError: Internal server error`
- 原因: MCPサーバは起動時にRDSへの接続プール(psycopg_pool)を開いて持ち続ける。そのプロセスは約1時間前から動いていて、
  使われていない間に接続が切れていた。プールは切れていることを確かめずに渡した。誰が切ったか(RDS側か基盤か)は確かめていない
- 修正: 渡す前に接続を確かめる`check=AsyncConnectionPool.check_connection`([system/mcp_server/server.py](../system/mcp_server/server.py))。
  確認の往復ぶん、検索が少し延びるはず(未計測)
- 見落としやすい点: 起動直後のテストでは起きず、しばらく使われなかった後にだけ起きる
