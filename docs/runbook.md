# 切り分けの手順書

事例ごとに「症状 → 最初の仮説 → 決め手になったspan・属性 → 判断 → 修正 → 修正の確かめ」の順で書く。
「修正の確かめ」は、直した後に同じ条件で症状が消えたのをトレースで見たか(済み・未・対象なし)。
「起きる場所」は、どこでも起きる(コード・設定・LLMの性質による)か、この基盤だから起きる(AgentCore・クラウドのSDKなどの都合による)か。
オンプレ側は測っていないので、一般的な情報と、手元だけで動かす形(llama.cpp・faiss・SQLite)で起きたかで判断した。
根拠のトレースは[traces/](../traces/)に置く。waterfallのHTMLは、GitHubではソースが表示されるので、ダウンロードしてブラウザで開く。番号は下の[事例の一覧](#事例の一覧)の番号。
AWSの振る舞い(AgentCore Runtimeの中継・セッション・メトリクス等)は、2026年11月時点、Runtime V1(初期値)で確かめたもの。サービス側の変更で変わりうる。

## 直すかどうかの判断

- 失敗(エラー・応答が返らない・タイムアウトに届く)は直す。起動や接続の切り替わりで、たまにしか出ないものも含む
- 遅れは、その遅れが乗る質問で、「答えが見え始めるまで」か「答えが終わるまで」のどちらかを約20%以上延ばすなら直す。今のAIチャットは答えを流しながら返すのが
  普通なので、見え始めを主に見る。見え始めは、最後の答え(ツールを呼ばなかったLLMの呼び出し)が始まるまでで、サーバ側のトレースから
  計算する(最後のchat spanの開始＋そのTTFT)。ツールの前の前置き(「検索します」等)が先に見えても、その時刻は記録だけにする。
  反復上限・エラーで終わった回は「答えなし」として時間を出さない(上の失敗として扱う)。「お待ちください」のような文で終わった回は
  答えとして時間を出し、文面と`stop_reason`を残す(答えの中身の良し悪しは測らない)。
  見え始めが数秒と小さいと割合が大きく出やすいので、割合と一緒に秒数も並べる。
  乗るのが一部の質問・回だけ(新しいセッションの最初だけ等)なら、そう書く。
  20%は、人が所要時間の差に気づく目安として引かれる値(Seow『Designing and Engineering Time』2008。原典は未確認で、二次情報には18%とするものもある)。
  業界で決まった基準ではない。実際の利用者が来たら、目標(SLO)を決めて見直す
- 回数が少ない(1条件3〜6回)ので、平均やp95ではなく、範囲(最小〜最大)と1問に占める割合で書く
- 計装の正しさに関わるもの(測る仕組みが測る対象を遅くする、トレースが切れる)は、遅れの大きさに関係なく直す
- 直さない遅れも、起きる場所と大きさを書く。「起きる場所」(誰の持ち物か)と「判断」(直すか)は別の行にする
- 仕込んだ落とし穴(番号の付いた事例)は、教材として直す。この基準は、自然に起きたものと観察に使う

## 気づき方(メトリクス)

この手順書は、遅れや失敗に気づいた後の切り分けを扱う。気づく側(メトリクス・アラーム)は作っていないが、各事例が既定のメトリクス
(vLLMの`/metrics`、CloudWatchの`AWS/Bedrock-AgentCore`・`AWS/RDS`)に映るかを、残っていた値で確かめた(確認)か、仕組みからの見込みかに分けて書く。

| 事例 | 映るメトリクス | 状態 |
|---|---|---|
| #10 プロンプトの先頭が毎回変わる | vLLMのプレフィックスキャッシュの当たる割合(`prefix_cache_hits_total`÷`prefix_cache_queries_total`)。基準は約89%、先頭の時刻ありは約0.5% | 確認 |
| #12 推論サーバの待ち行列 | vLLMの`request_queue_time_seconds`・`num_requests_waiting`・`num_preemptions_total` | 見込み(待ちが起きず、動くところは見ていない) |
| M1 ツール定義の膨張 | vLLMの`prompt_tokens_total`の増え方 | 見込み |
| #9 長い出力 | vLLMの`request_success_total`の`finished_reason="length"`、出力トークン数 | 見込み |
| M2 毎回のコールドスタート | MCPサーバのRuntimeの`Sessions`(新しく作られたセッションの数)が`Invocations`に近づく | 見込み |
| 同じ質問が2重に処理される | エージェントのRuntimeの`Invocations`が、送った数より多い | 見込み |
| 割り当ての前に作ったDBの接続が、切れている | エージェントのRuntimeの`UserErrors`(11-05の失敗は`SystemErrors`ではなくこちらに1件。エージェントの500を、AgentCoreは呼び出し側に424で返した)。`SystemErrors`だけを見ると見逃す | 確認 |
| 利用者が切っても、エージェントが答えを最後まで作る | 映らない。止まらないときは`stop`が増え、止まったときもvLLM 0.31.0は切られた要求を数えない(`abort`は0のまま)。切った質問はエージェントのRuntimeの`Latency`がヘッダまで(83〜97ms)で、エラーにもならない。止めた回数は`StopRuntimeSession`のメトリクス(セッションごとの`Invocations`)で数えられる | 確認 |
| セッションが終わった後も、DBの接続が1〜6分残る | RDSの`DatabaseConnections`。合計だけで、どのセッションの接続かは分からない(1分ごとの最大が、`pg_stat_activity`で数えた本数と一致した)。セッションを止めた分は次の1分で減るが、きれいに閉じたかはログでしか分からない | 確認 |
| AgentCoreの`Latency` | SSEで返すと応答のヘッダまでしか測らない | 確認 |
| 15分以上あけた後の、最初のツールの呼び出しが遅い | MCPサーバのRuntimeの`Latency`には入る(MCPサーバはSSEで返さない)が、普段の分ごとの最大(0.37〜0.86秒)に埋もれる。`Sessions`は増えた(S1は同じセッションIDでも新しいセッションとして数えられた) | 確認 |
| #1・#2・#3・#5、計装の保存、TTFTの約500ms、`MCP send`の隙間、新しいセッションの約1秒 | 既定のメトリクスには原因が映らない。答え全体の時間のメトリクスがあれば、遅れとしてだけは映る | 見込み |

上限に近づく前に気づくには、RDSの`DatabaseConnections`に、使える本数の約8割でアラームを置くのが一般的(作っていない)。

## 1 独立したツール呼び出しを、1つずつ待つ(逐次await)

- 起きる場所: どこでも(コードの書き方)
- 再現: 注入(`PITFALLS=1`、2026-11-05、GPUの1回目)。計装と手順書を確かめるために入れた
- 条件: 「A社の未出荷の受注と、品目X001の在庫は?」を、温めたセッションで3回。LLMは1つの返事でツールを2〜3個呼ぶ
- 症状: 1問が約44秒(基準は約42.5秒)。差はツールの数と待ち時間で決まり、この質問では2秒弱
- 決め手: エージェント側の`execute_tool`(と`MCP send`)の開始が階段状になる。前の呼び出しが終わった時刻に、次が始まる。
  2回目の返事では、`find_records`が28.50秒から0.92秒、`aggregate_records`が29.42秒から。基準では2つとも同じ時刻に始まる
- 修正: `asyncio.gather`で同時に呼ぶ(基準の書き方、[system/agent.py](../system/agent.py))
- 修正の確かめ: 済み(基準の回。同じ質問で、`execute_tool`が同じ時刻に始まり、1問が約44秒から約42.5秒)
- 似た症状との見分け: #2とは、どちら側が階段になるかで分かれる(下)。イベントループの遅延を測る計装は要らなかった
- 根拠のトレース: [#1あり](../traces/1/gpu1-q2.html)、[基準](../traces/base/gpu1-q2.html)

## 2 asyncの中のブロッキング呼び出し(同時に呼んでも順になる)

- 起きる場所: どこでも(コードの書き方)
- 再現: 注入(`PITFALLS=2`、MCPサーバのモックが`time.sleep`で待つ。2026-11-05、GPUの1回目)
- 条件: #1と同じ質問を3回
- 症状: 1問が約44秒。#1とほぼ同じで、合計時間だけでは区別できない
- 決め手: エージェント側の`execute_tool`は同じ時刻(9.55秒)に3つそろって始まるが、サーバ側の`tools/call`の開始が
  9.61 → 9.83 → 10.07秒と階段状になる。`POST /mcp`は9.83秒に受け付けているのに、中の`find_records`は10.07秒まで始まらない。
  サーバのイベントループが`time.sleep`の間止まり、受け付けた次のリクエストに進めない
- 修正: 非同期の待ち(`asyncio.sleep`、非同期のクライアント)か、スレッドへ逃がす(`asyncio.to_thread`)
- 修正の確かめ: 済み(基準の回のモックは`asyncio.sleep`で待つ。同じ質問で、サーバ側の`tools/call`3つが17msの間にそろって始まる)
- 似た症状との見分け: #1はエージェント側が階段、#2はエージェント側がそろってサーバ側が階段。
  MCPサーバ側の計装が無いと、#2は「ツールの応答が遅い」としか見えない(エージェント側では、各`MCP send`がサーバでの処理より長くなる。
  `aggregate_records`は処理0.24秒に対して`MCP send`が0.54秒で、前の処理の終わりを待った分が乗る)
- 根拠のトレース: [#2あり](../traces/2/gpu1-q2.html)、[基準](../traces/base/gpu1-q2.html)

## 3 エージェントループの過剰反復(同じtoolを何度も呼ぶ)

- 起きる場所: どこでも(LLMとエージェントループ)
- 再現: 注入では起きなかった。2026-10-08に、中身の無い`{"status": "ok"}`だけを返すモックで2Bが同じ集計を繰り返して
  打ち切られた([設計書](DESIGN.md)の§7の4)が、spanを付ける前で記録が無い
- 試したこと:
  - 2026-11-04: 同じ形のモック(`PITFALLS=3`)で、手元の2B(llama.cpp)に仮の質問を6回。繰り返しは0回で、どれもLLM 2〜3回で止まった
  - 2026-11-05(GPUの1回目、Qwen3-8B): 業務データを使う仮の質問5問を1回ずつ、うち2問は2回目も。5問のうち0問で、同じツールを
    同じ引数で2回以上呼んだ。どれもLLM 2〜3回で止まり、基準より短くなった(「A社の未出荷の受注は?」は21.8秒 → 10.5秒)。2回目の2問は1回目とほぼ同じ時間
- 自然には起きた: 基準の回の「品目X001の入荷待ちの発注は?」で、1回だけ`find_records`を呼び直し続け、反復の上限(`max_turns_exceeded`)まで
  115秒かかった(下の「自然に発生: 同じ質問が2重に処理される」の1つ目の処理)。決め手は`invoke_agent` spanの`error.type`と、
  その下の`execute_tool`の数。同じ質問でも、ほかの回はLLM 2〜6回で止まった
- 修正: 反復回数の上限(今のエージェントにある)。上限で止まった答えは返らないので、その時間はまるごと無駄になる
- 修正の確かめ: 上限が働くことは確かめた(自然に起きた回が115秒で止まった)。繰り返しそのものを減らす修正は無い
- 根拠のトレース: [#3あり、「A社の未出荷の受注は?」](../traces/3/gpu1-q1.html)、[自然に上限まで繰り返した回(1つ目の処理)](../traces/retry-duplicate/gpu1-q5.html)

## 自然に発生: 計装の保存がイベントループを止める

[設計書](DESIGN.md)の§7の2・3・11から。

- 起きる場所: どこでも(保存の方式。送り先がCloudWatchだと、1回の送信が長いぶん大きく出る)
- 再現: 自然に発生(2026-10-04、段階2a。2026-10-27に、送り先をCloudWatchにしたときにも同じ形で起きた)

  CloudWatchへ送った試しのスクリプトでは、子spanを1本作って閉じただけの親spanが537msになった
- 最初の仮説: 記録に無い(最初に、通信かサーバの中かを分けた)
- 決め手(順に):
  - HTTPの層のspan(`POST /mcp`)を足すと、差は通信ではなくサーバの中、それも「ツール処理が終わってから応答を送り始めるまで」にあった
  - asyncioのデバッグモード(`loop.slow_callback_duration`を20ms)で、その区間にイベントループが30〜70ms止まっていた。サーバの計装をオフにすると消えた
  - 保存1回ごとに時間を測ると、`tools/call` spanの保存だけがときどき約67msかかっていた。SQLiteは、前の書き込みから100ms以上空くと
    commitに65〜75msかかる(連続なら4ms)

  (#2と同じ形。`span.end()`も`export()`も同期の関数で、`await`を入れる余地が無い)。CloudWatchへの送信では、署名とHTTPSの往復を待つので1桁大きくなる
- 判断: 直す。遅れは1問の1%未満だが、計装が測る対象を遅くするため
- 修正: `BatchSpanProcessor`(キューに入れ、別のスレッドがまとめて保存する)に変えた。差は3〜11msになった。
  今はどのプロセスも`build_tracer_provider(..., batch=True)`([tracing/instrumentation.py](../tracing/instrumentation.py))
- 修正の確かめ: 済み(上の差が3〜11msになった)
- 代わりに起きること: 保存は最大500ms(`BATCH_EXPORT_INTERVAL_MS`)遅れる。終了時に`shutdown()`しないと、キューに残ったspanが失われる
- 似た症状との見分け: #2(ツールの中のブロッキング呼び出し)とは、計装をオフにすると消えるかで分かれる。
  消えるなら計装、消えないならツールのコード。spanを作ること自体は1個あたり約0.03msで、問題は保存のほう
- 見落としやすい点: 測るための仕組みが、測っている対象を遅くする。手元のSQLiteやこのPCのディスクに固有の部分はあるが、
  「同期的な保存やログの送信がリクエストの処理を止める」形は実務でも起きる

## 観察: 新しいセッションでも、遅れは約1秒

- 起きる場所: この基盤だから(AgentCoreのセッションの起動)
- 判断: 直さない(記録だけ)。こちらで減らせるのは最初の`tools/list`の約0.09秒で、見え始め(この質問で約10秒)の1%未満。
  残りはAgentCore側の処理で、こちらからは減らせない
- `--cold`(毎問を新しいセッション)で、「A社の未出荷の受注は?」22.6秒、「A社の未出荷の受注と、品目X001の在庫は?」43.4秒。
  温めた回より約1秒長いだけで、予想(5〜7秒)よりずっと小さかった(2026-11-05)
- 内訳(2026-11-09に、同じ回の温めた質問のトレースと比べた。LLMの入力トークンと時間はほぼ同じで、差は最初の部分だけ):

  | どこ | 1問目 | 2問目 |
  |---|---|---|
  | 呼び出し側のspanのうち、AgentCoreのspan(`AgentCore.Runtime.Invoke`)の外側 | +約270ms | +約60ms |
  | AgentCoreのspanの開始から、`invoke_agent`の開始まで | +326ms | +338ms |
  | 最初の`tools/list`(温めた回では温め用の質問で済んでいる) | +88ms | +97ms |
  | 合計(呼び出し側の時間の差) | +806ms | +883ms |

  1行目は、呼び出し側とAWSで時計が違うので、開始時刻ではなく長さの差から出した。2行目の間、こちらのコードはほとんど動かない
  (温めた回では約50ms)。前もって起動したコンテナをセッションに割り当てる処理と見ているが、AgentCoreの文書では確かめていない
- `tools/list`を起動時(割り当ての前)に送れば約0.09秒は消せるが、DBのプールを開くきっかけも割り当ての前に戻り、
  「割り当ての前に作ったDBの接続が、切れている」が再発するので採らない
- 根拠のトレース: [traces/cold-session/](../traces/cold-session/)(`gpu1-q1-cold`・`gpu1-q1-warm`)

## 観察: セッションが終わった後も、DBの接続が1〜6分残る

- 起きる場所: この基盤だから(セッションの終わりに、MCPサーバのmicroVMが接続を閉じずに止まる)
- 判断: 今は記録だけ。利用者に見える遅れではないが、繁忙時の接続の数に効く。寿命を「最後の使用から15分＋1〜6分」で数えると、
  [DESIGN](DESIGN.md) §6の7の仮定(300人・1日3問・繁忙時は3倍、1問ごとに新しいセッション)で約380〜500本になり、
  確かめた`max_connections`の400を超えうる。打ち手は、セッションを見積もりの規模まで増やして決めるもので、その回はやっていない(実験は終えた)
- 見積もりの式: 接続の数 ≒ プールの本数(4) × 新しいセッションが来る速さ × (セッションが使われている時間 ＋ 15分 ＋ 1〜6分)
  - 「1問ごとに新しいセッション」は悲観的な仮定。会話ごとに同じセッションを使い回せば、セッションの数は減る
  - RDSは管理用の接続の枠を取っておくので、アプリが使える本数は400より少ない(正確な数は確かめていない)
  - 上限に届いたときの壊れ方は確かめていない。新しい接続が断られ、検索のツールがエラーを返すと見ている
- 打ち手の候補(確かめたのは最後の行の`StopRuntimeSession`だけ):

  | 打ち手 | 効くところ | 引き換え |
  |---|---|---|
  | プールの`min_size`を下げ、`max_idle`を15分より短くする | 使われない接続を、microVMが止まる前にこちらから閉じる | 次の検索で接続を作り直す分(約0.1秒〜1秒)が乗りうる |
  | RDSの`tcp_keepalives_idle`を短くする | 止まった後の1〜6分だけが縮む | 15分の部分は残る |
  | RDSの`idle_session_timeout` | 使われない接続をDB側から切る | 生きているセッションの接続も切り、「割り当ての前に作ったDBの接続」と同じ形の遅れが戻りうる |
  | RDS Proxy | DB側の本数を抑える(多くのクライアントから繋ぐときのAWSの推奨) | 各microVMが作る本数は減らない。費用とIAM認証の設定が増える |
  | AgentCoreの使われない時間(既定15分)を短くする | 生きているセッションが減る | 新しいセッションの起動とMemoryの読み戻しが増える |
  | 会話の終わりに`StopRuntimeSession`でMCPのセッションも止める | 止めた時点で接続が閉じる(2026-11-11に確かめた、下) | 呼び出し側が会話の終わりを知る必要がある。MCPのセッションIDはエージェントのプロセスが持つ |
- 2026-11-09、GPUの3回目で、7セッションの28本を、作られた時刻で見分けて追った(`pg_stat_activity`を30秒ごと、RDSの`log_disconnections`):
  - 28本すべてが、RDSのログで`could not receive data from client: Connection timed out`で切れていた。きれいに閉じた接続は無い。
    MCPサーバのログにも、終了処理(uvicornのshutdown・lifespanの終わり)の行が1つも無い
  - 切れた時刻は、どの接続も「その接続の最後の使用＋5分の倍数＋約1分」。RDSの生存確認(`tcp_keepalives_idle` 300秒・`interval` 30秒・`count` 2)が、
    応答の無い相手に気づいた時刻にあたる
  - 最後の使用から閉じるまでは、約16分と約21分の2群に分かれた:

    | 場合 | セッション | 閉じるまで |
    |---|---|---|
    | セッションの最後のMCPへの要求が、その接続の最後の使用と同時 | 1問だけのS0・S1・s2 | 約16分(止まった直後の生存確認で気づく) |
    | 最後の使用の後に、別の要求があった | 基準・条件のずれの確認・s3 | 約21分(15分の確認には間に合い、次の確認で気づく) |

  - 決め手: 種類ごとのツールの回では、同じセッションの4本が分かれた。最後に使ったのが11:36:00の1本は16.1分で、11:34:07の3本は21分で閉じた。
    microVMはセッションの最後の要求から15分で止まり、15分が生存確認の5分の倍数なので、どちらの確認に先に当たるかで2群になる
- 切り替え(Runtimeの更新)の後も、古いセッションの接続は同じように残った
- 2026-11-11、GPUの4回目の前に、手元からMCPのRuntimeを直接呼んで検索させ(4本ができる)、そのセッションを`StopRuntimeSession`で止めた(2回)。
  2回とも、止めた同じ秒にMCPサーバのログに終了の4行(`Shutting down`〜`Finished server process`)が出て、RDSのログでは4本ともふつうの
  `disconnection`で閉じた(`could not receive data`は無い)。止めればプールの`close()`まで動く。RDSの`DatabaseConnections`も、次の1分で4本減った
- 見落としやすい点: 合計の`DatabaseConnections`では、他のセッションと混ざって見えない。数えるときは「処理中の質問の数」ではなく「生きているセッションの数＋止まってからの数分」で数える
- 根拠: トレースではなく、RDSの接続ログと`pg_stat_activity`の記録(リポジトリには置いていない)

## 観察: AgentCoreの`Latency`は、ストリーミングでは答えの長さを表さない

- 起きる場所: この基盤だから(AgentCoreのメトリクスの測り方)
- 判断: 対象外(読み方の注意)。答えの時間は、呼び出し側で測る(`caller.time_to_first_text_ms`と、呼び出し側のspanの長さ)
- CloudWatchのメトリクス`Latency`(`AWS/Bedrock-AgentCore`、`InvokeAgentRuntime`)は、同じエージェントで返し方だけが違う回で、次のようになった:

  | 回 | 返し方 | `Latency` | 答えが終わるまで |
  |---|---|---|---|
  | 2026-11-05・11-07 | 答えを最後にまとめて返す(JSON) | 1.5〜115秒 | 合う |
  | 2026-11-09 | SSE(2026-11-08から) | 0.07〜0.57秒 | 6〜40秒 |

- SSEのときの値は、エージェントが応答のヘッダを返すまでと合う(4秒で切った回は122ms、トレースの`AgentCore.Runtime.Invoke`は0.08秒)
- 公式の説明は「要求を受けてから、最後の応答トークンを送るまで」([AgentCore generated runtime observability data](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-runtime-metrics.html))で、
  SSEでは成り立たない。同じ名前空間の`Duration`は、どの点でも`Latency`と同じ値で、このページに載っていない。
  `OverheadLatency`(AgentCore自身の時間)はRuntime V2向けで、この回(V1)には出なかった
- 見落としやすい点: 返し方をSSEに変えると、監視のグラフでは「速くなった」ように見える
- 根拠: CloudWatchのメトリクス(`get-metric-statistics`)

## 観察: 15分以上あけた後の、最初のツールの呼び出しが遅い

- 起きる場所: この基盤だから(AgentCoreの中継の中。microVMの起動ではない、下)
- 判断: 原因は突き止められていない。今は回さない。S0の続きでは見え始め(呼び出し側で2.4秒)の約35%で基準の20%を超えるが、
  1秒未満の遅れで、答え全体は10〜40秒かかり、11-11の8回では再現しなかった。確かめ方は下に書いた
- 2026-11-09、GPUの3回目。MCP側のセッションが15分で終わった後の、最初のMCPへの呼び出し:

  | 回 | 呼び出し | AgentCoreの中継の時間 | MCPサーバの中 | いつもより |
  |---|---|---|---|---|
  | S1の検索(エージェントは生きていて、MCPだけ止まっていた) | `tools/call retrieve_documents` | 718ms | 161ms | 約0.55秒 |
  | S0の続き(エージェントもMCPも止まっていた) | `tools/list` | 936ms | 2ms | 約0.85秒 |
  | 同じ回の新しいセッション(7つ) | 最初の呼び出し | 20〜39ms | ほぼ0 | - |

- 待っているのは、AgentCoreの中継の中。**microVMの起動ではない**: 遅かった2回を受けたMCPサーバのプロセスは、どちらも18〜28分前から起動していた
  (S1の検索は11:45:17から、S0の続きは11:39:57から)。その直後にログに出る`Started server process`は、割り当ての後の補充だった。
  AgentCoreはRuntimeを作るときに約10個のプロセスを前もって起動し、セッションに1つ割り当てるたびに1つ補充する(§8の11-06の「接続が40本」と同じ形)
- 2026-11-10に「そのたびに新しいmicroVMの起動」「止まったmicroVMのIDのために起動し直した」と書いたのは、ログの読み違いだった(上の補充の行を起動と読んだ)
- 2026-11-11、GPUの4回目で、手元からMCPのRuntimeを直接呼んだ(新しいセッションか、前のID。最初の要求`server/discover`の長さ):

  | 回 | 最初の要求 | AgentCoreの中継 | 受けたプロセスの起動からの秒数 |
  |---|---|---|---|
  | (a) Runtimeを作って約3分・約50秒、新しいセッション | 0.75・0.79秒 | 0.38・0.43秒 | 200・45秒 |
  | 新しいセッション(止める確かめの2回) | 0.64・0.74秒 | 0.42・0.50秒 | 298・538秒 |
  | (b) 20分以上だれも呼ばない後、新しいセッション | 0.86・0.83秒 | 0.61・0.51秒 | 2419・1197秒 |
  | (c) 一度呼んだIDで16分後 | 0.87・1.04秒 | 0.63・0.65秒 | 2219・2245秒 |

  - 8回とも、前もって起動してあったプロセスが受けた(起動からの秒数はspanの`process.creation.time`、PR #43)。(c)では、前のプロセスは15分で止まり、
    同じIDの続きは別のプロセスが受けた
  - 空けた後(b・c)は、中継が0.1〜0.2秒長い。11-09のような約0.7秒の上乗せは無かった
  - ただし比べ方が弱い: 手元からネット越しに呼んだので、新しいセッションでも中継に0.4〜0.6秒が乗る(11-09はAWSの中のエージェントからで20〜39ms)。
    約0.7秒の上乗せが無かったことの、弱い根拠にとどまる
- 確かめるなら: 同じリージョンの中(エージェントのRuntimeか、VPCの中のEC2)から呼び、11-09と同じ条件(Runtimeの切り替えの後、MCPだけ15分止める)で、
  呼ぶたびに中継の時間(`AgentCore.Runtime.Invoke`)と受けたプロセスの起動時刻を記録する。11-09は切り替え(Runtimeの更新)の後の呼び出しで、11-11は切り替えなし
- 直すなら: 中継の中なので、こちらの設定では縮められない見込み。15分より短い間隔でMCPに軽い呼び出しを送って止まらないようにすると、
  その分microVMとDBの接続が残り続け、上の「DBの接続が1〜6分残る」の数が増える
- 見落としやすい点: MCPサーバのログの時刻はspanより6〜8秒遅い(取り込みの時刻)。補充の`Started server process`は、割り当ての直後に出るので、
  その要求のための起動に見える。どのプロセスが受けたかは、ログのストリーム名(プロセスごと)か、spanの`process.creation.time`で見る

  [20分空けた後の新しいセッション(11-11)](../traces/mcp-after-idle/gpu4-after-20min-new.html)、[Runtimeを作った直後(11-11)](../traces/mcp-after-idle/gpu4-just-created.html)
