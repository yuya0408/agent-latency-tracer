# ADR-0003: 事例の再現は、GPUで動かす8Bで行う

- Status: Accepted
- Date: 2026-10-14

## 結論(Summary)

- 事例の再現(段階6)は、GPUのEC2(g6.xlarge、NVIDIA L4)で動かすQwen3-8Bで行う。エンジンはADR-0004。
- 段階5までは手元のCPUのllama.cpp(Qwen3.5-2B)のまま進める。つながることを確かめるだけで、LLMの性能は効かないため。
- モデルの大きさは比べない。答えの正しさも目的の外。
- 2026-10-11の「2Bのまま進める」を改めた決定。

## 背景と問い(Context and Problem Statement)

2026-10-11に、事例の再現も手元の2Bで行うと決めていた。理由は「事例の遅さはこちらで作り込むもので、
LLMに要るのはツールを呼ぶ・複数頼む・止まることだけ」だった。

ところが、手元のCPU(4スレッド)で2Bを動かすと、仮の質問6つで1問18〜63秒かかり、そのほとんどがLLMだった。
ツールの実行は1回1秒未満だった(DESIGN §8)。事例の差は数十ミリ秒〜数秒なので、LLMの時間に埋もれる。
また、どの遅れが体感に効くかの比率が、GPUで推論する実際のサービスと大きく違ってしまう。
10-11の判断はこの点を見落としていた。

問い: 事例を再現するLLMを、どこで、どの大きさで動かすか。

## 検討した案(Considered Options)

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 手元のCPUで2Bのまま(10-11の決定) | 却下 | 1問のほとんどをLLMが占め、事例の差が埋もれる(Context) |
| 手元のCPUで8B | 却下 | bf16では約16GBで、PCのメモリ(13.74GB、WSLが使えるのは約6GB)に載らない。量子化すれば載りうるが、2Bより遅くなり、埋もれる問題は悪化する(推定、測っていない) |
| GPUのEC2で8B | 採用 | 決定を参照 |
| マネージドのAPI(Bedrockなど) | 扱わない | プロジェクトの前提が自前ホストのLLM。待ち行列(#12)など、エンジンの中を見る事例が再現できない |
| モデルの大きさを比べる | 扱わない | 遅延の切り分けを学ぶ目的に効かない |

## 決定(Decision Outcome)

- 段階5bを新しく設け、GPUのEC2を同じVPCに置き、エージェントもAgentCore Runtimeへ移す(ADR-0001)。
- インスタンスとモデルは`toolcall-serving-bench`と同じg6.xlarge・Qwen3-8Bにし、そちらで組んだGPUの環境を流用する。
  8Bはbf16でL4(24GB)に載る。
- `toolcall-serving-bench`を先に終え、同じ月にGPUを回さない(予算の月60ドルを同じアカウントで分け合うため)。

## 影響(Consequences)

- 得るもの: 1問の中でLLMが占める割合が、実際のサービスに近くなる。5bの実測ではTTFT 84ms、トークンの間隔約60ms(DESIGN §8)。
- 失うもの: GPUの費用(1時間約$1.17)と、起動に約12分半、destroyに約11分半。段階が1つ増えた。
- 残る穴: 1問あたりの時間を8Bでまだ測っていない(段階6の最初の回で測る)。
